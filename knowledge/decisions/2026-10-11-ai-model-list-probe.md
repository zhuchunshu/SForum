# Decision: AI 模型列表探测允许使用未保存的表单值，且不写执行记录

## Status

Accepted (2026-10-11)

## Context

控制台的「连接配置」里，模型标识原本只能手填。运营者必须先知道供应商支持哪些模型
（DeepSeek 有 `deepseek-chat` / `deepseek-reasoner`，兼容网关的命名更是各不相同），
而在新建自定义供应商时，这一点最不显然。

要做「一键获取模型列表」，有三个必须拍板的问题：

1. 探测用哪一份配置？已保存的文档，还是表单里正在编辑的值？
2. 待保存的密钥明文能不能随探测请求发出？
3. 探测要不要经过网关的闸门、用量与执行记录？

约束来自仓库既有约定：
- 密钥明文只在 `PUT /admin/ai/profiles/:profileId/credential` 这一次请求里存在，
  设置文档只保存 `sforum.secret://` 引用；
- 所有出站必须走 `Support/OutboundHTTP` 的公网校验与超时；
- 执行记录（`ai_executions`）是成本口径与审计的依据，不能被非补全调用污染。

## Decision

1. **探测参数由请求携带，且全部可选。** `POST /admin/ai/profiles/:profileId/models`
   接受 `{baseUrl?, protocol?, apiKey?}`：缺省时用已保存的 profile 与 Secret Store
   里的密钥，带了就用请求值。这样「填地址 → 填密钥 → 获取列表 → 选模型 → 保存」
   是一条直线，不需要先把一份没有模型的配置存进库。
2. **明文密钥可以在这次只读请求里传输，但不进入任何持久化路径。** 它与 credential
   端点处于同一信任级别（`ai.manage` 管理员显式操作、HTTPS、同源会话 + CSRF），
   且不写库、不记录、不回传。写入密钥仍然只有 credential 一条路。
3. **不走网关，不写用量与执行记录。** 模型列表不是补全调用，没有 token、没有费用。
   出站改走同一个 `HTTPInvoker`（新增 `Execute` 返回原始状态码与响应体），因此 SSRF
   校验、超时与 1 MiB 响应体上限仍然只有一处实现。
4. **供应商层面的失败是结论，不是 5xx。** 与诊断一致：返回 200 +
   `reason=provider_failed` + 可读 `error`，由界面就地解释。配置层问题（缺密钥、
   地址非法、profile 不存在）仍然 4xx。
5. **探测不要求 model 已填。** `Profile.WithProbe` 只校验协议与地址；要求先填模型
   会让这个按钮在最需要它的场景里不可用。

## Consequences

- 未保存的「自定义」供应商也能探测，代价是服务层多了一条「设置里找不到就用请求地址
  构造一次性 profile」的分支；没有地址时仍然 404，不会静默用别的端点。
- 明文密钥出现在一个额外的请求体里。风险由第 2 点收敛，缓解手段是：不落库、不进
  日志、不回传、不缓存；前端把它当作一次性参数，不写入任何存储。
- 探测结果不持久化，刷新后需要重新获取。下拉列表按 profile 隔离，切换供应商不会
  串用上一个端点的模型。
- 若将来给模型列表加缓存或价格预填，必须重新评估第 3 点，避免把探测变成一次隐式的
  计费调用。
