## 根因

`apps/web/scripts/dev-theme-runtime.mjs`（开发）和 `apps/web/scripts/runtime.mjs`（生产）的 `main()` 启动时序有缺陷：

```js
async function main() {
  await proxy.listen()          // (1) supervisor 先对外监听 3000
  // ...
  await startDev('startup')     // (2) 这时才开始 spawn nuxt dev 子进程
}
```

supervisor 在 `proxy.listen()` 完成后就占用对外端口，但此时 `activeTarget` 仍是 `null`（nuxt dev 子进程还没 spawn / 没通过健康检查）。从 `proxy.listen()` 到 `proxy.setTarget()` 之间这段冷启动窗口（开发最长 120s、生产 30s），所有入站请求走 `theme-proxy.mjs:30-35` 的 `activeTarget === null` 分支，直接返回 **502 "SForum web is starting up"**。

这正好解释用户报告的两个症状（"启动后第一次访问"触发）：

1. **登录页白屏**：`/login` 是 `ssr: false`（纯 SPA），HTML 只有一个空 `<div id="__nuxt">`，靠浏览器加载 `/_nuxt/.../entry.async.js` 挂载。冷启动窗口里这个 `<script>` 请求拿到 502 → JS 加载失败 → Vue app 没机会挂载 → 白屏。SPA 页面对此最敏感，所以"尤其是登录页"。
2. **提交表单 502**：`/api/v1/auth/login` 同样经过 supervisor（3000）→ 502。

蓝绿切换（主题切换）场景有旧子进程兜底，不受影响；问题只在初次冷启动。

## 修复方案

调换 `main()` 里的启动顺序：**先等子进程 ready（`startXxx` 通过健康检查、`proxy.setTarget` 被调用），再 `proxy.listen()` 对外监听。** 子进程 ready 前不占用对外端口，浏览器访问会得到 ECONNREFUSED（清晰的"服务未起"信号），而不是误导性的 502 + 空 HTML 白屏。

### 改动 1：`apps/web/scripts/dev-theme-runtime.mjs` 的 `main()`

```js
async function main() {
  fs.mkdirSync(releaseRoot, { recursive: true })
  // 先注册信号处理：启动期间收到信号也要能优雅退出
  process.on('SIGTERM', async () => {
    stopChild(child)
    child = null
    await proxy.close()
    process.exit(0)
  })
  process.on('SIGINT', async () => {
    stopChild(child)
    child = null
    await proxy.close()
    process.exit(0)
  })
  // 先启动 nuxt dev 子进程并等它通过健康检查，再对外监听。
  // 否则冷启动窗口期 activeTarget===null，所有请求返回 502，
  // SPA 页面（如 /login）拿不到 entry.async.js 就白屏。
  await startDev('startup')
  if (!proxy.getTarget()) {
    console.error('[sforum-dev-runtime] initial nuxt dev did not become ready; exiting')
    process.exit(1)
  }
  await proxy.listen()
  console.log(`[sforum-dev-runtime] proxy listening on ${externalHost}:${externalPort}`)
  console.log(`[sforum-dev-runtime] public URL: ${publicDevUrl}`)
  fs.watch(releaseRoot, scheduleRestart)
}
```

要点：
- `proxy.listen()` 移到 `startDev()` 之后；`startDev` 内部 `replaceTarget` 成功才会 `setTarget`，此时 listen 才会让端口真正可服务。
- 加 `proxy.getTarget()` 检查：初次启动失败（健康检查超时、子进程崩溃）时明确报错退出，而不是 listen 后继续返回 502。`getTarget()` 是 `theme-proxy.mjs:57-59` 已暴露的方法，返回 `activeTarget`。
- 信号处理移到 `startDev` 之前：启动期间收到 SIGTERM/SIGINT 也能优雅退出（`proxy.close()` 在未 listen 时调用是安全的，`server.close()` 直接回调）。
- `fs.watch` 仍在 listen 后注册：启动期间 current.json 变化概率极低，且 `startDev` 完成后立即注册。

### 改动 2：`apps/web/scripts/runtime.mjs` 的 `main()`（生产，同样修复）

同样的调换：

```js
async function main() {
  fs.mkdirSync(releaseRoot, { recursive: true })
  process.on('SIGTERM', async () => {
    stopChild(child)
    child = null
    await proxy.close()
    process.exit(0)
  })
  process.on('SIGINT', async () => {
    stopChild(child)
    child = null
    await proxy.close()
    process.exit(0)
  })
  await startCurrent()
  if (!proxy.getTarget()) {
    console.error('[sforum-web-runtime] initial server did not become ready; exiting')
    process.exit(1)
  }
  await proxy.listen()
  console.log(`[sforum-web-runtime] proxy listening on ${externalHost}:${externalPort}`)
  fs.watch(releaseRoot, scheduleRestart)
}
```

### 不改动的部分

- **`theme-proxy.mjs` 不改**：`activeTarget === null` 时返回 502 是合理的运行期兜底（upstream 崩溃、崩溃恢复窗口）。冷启动竞态通过 listen 时序解决，不需要给代理核心加"请求排队/等待"的复杂逻辑——那会让浏览器请求挂起最长 120s，体验比 ECONNREFUSED 更差。
- **`server/routes/api/v1/[...path].ts` 不改**：它的 502 是后端 Go API（air 重启）不可用时 Nitro 的行为，是独立的另一层，且 `useAuthSession` 已有 `unavailable` 状态容错。本次只修冷启动竞态。
- **崩溃恢复逻辑不改**：`child.on('exit', () => setTimeout(() => startDev('nuxt-dev-restart'), 1000))` 保持原样。崩溃恢复期间会有短暂 502 窗口，但这是罕见情况（nuxt dev 崩溃），且那时 supervisor 已 listen，无法再"先 ready 后 listen"。用户报告的是冷启动，不是崩溃恢复。

## 验证

1. **手动复现修复前行为**（可选，确认根因）：停掉 supervisor，重启 `bun run dev`，立刻 `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3000/login`，预期看到 502。
2. **验证修复后**：改完后重启 `bun run dev`，立刻连续 `curl` 3000 端口——预期在 nuxt dev ready 前得到 ECONNREFUSED（连接被拒），ready 后才返回 200 HTML。
3. **正常流程回归**：nuxt dev ready 后，`/login` 正常渲染、`POST /api/v1/auth/login` 正常返回 401/200，无白屏。
4. **主题切换回归**：启动后改 `current.json`，确认蓝绿切换仍正常（`fs.watch` → `scheduleRestart` → `replaceTarget`，旧 child 兜底）。
