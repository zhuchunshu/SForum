# 帖子 URL 模式后台可切换 + 301 兜底 实施方案

## 目标与范围

让管理员在 **SEO 设置页**选择帖子详情页的 URL 形态,默认 `ID+slug`;切换模式或 slug 变更时,**旧 URL 自动 301 到规范新 URL**。

**v1 支持的 3 种模式**(默认值 `id_slug`):

| 模式 | 形态 | 后端查找 | 说明 |
|---|---|---|---|
| `id_slug`(默认) | `/t/123/hello-world` | 按 ID(已具备) | 最稳健 |
| `id` | `/t/123` | 按 ID(已具备) | 最稳定、无 SEO |
| `slug` | `/t/hello-world` | 按 slug(**需新增**)+ 全局唯一化 | 最短 |

> **暂不实现** `category_slug`(`/c/general/hello-world`):需分类联动且与 `/c/:slug` 列表路由消歧,工程量明显偏高,留作 v2。若你想要,告诉我即可加进来。

## 架构关键决策

### 1. 详情页改为 catch-all(模式切换的唯一可行路径)
Nuxt 文件路由无法运行时改形状(`/t/123`、`/t/hello`、`/t/123/hello` 是三种不同文件结构)。唯一出路:
- 把主题层 `t/[topicID]/[topicSlug].vue` 改造为 **`t/[...path].vue`**(catch-all)。
- 页面内根据当前配置的 `seo.topic_url_mode` 解析 `route.params.path[]`,规范化后做 301 / 渲染。
- 删除 `t/[topicID]/[topicSlug]/edit.vue` 的嵌套结构,把编辑页移到 `t/[...path]/edit.vue`(或用 query `?edit=1`),避免与 catch-all 冲突。

### 2. `forumTopicPath` 成为唯一 URL 出口
改造 `apps/web/app/utils/forumTaxonomy.ts:278` 的 `forumTopicPath`,让它**读取当前 mode** 并生成对应形态。8 处调用点(首页/分类/标签/用户/新建/编辑/详情)自动统一,无需逐处改。

```ts
// 新签名:读取 useWebOptions 的当前 mode
export function forumTopicPath(
  topic: Pick<ForumTopicSummary, 'id' | 'slug'>,
  mode: TopicUrlMode = 'id_slug'
): string {
  switch (mode) {
    case 'id':      return `/t/${topic.id}`
    case 'slug':    return `/t/${encodeURIComponent(topic.slug)}`
    default:        return `/t/${topic.id}/${encodeURIComponent(topic.slug)}`
  }
}
```
(为避免 SSR 状态读取耦合,mode 作为显式参数传入,调用方从 `useWebOptions` 取一次。)

### 3. 后端新增「按 slug 查找」+ slug 全局唯一(仅 `slug` 模式需要)
- 新增 `Store.GetTopicBySlug(ctx, slug) (TopicDetail, error)`(`forum/store.go` 接口 + `postgres_store.go` 实现 + `cached_store.go` 装饰)。
- 新增公开端点 `GET /api/v1/topics/by-slug/:slug`(controller + route)。
- **slug 唯一化**:`slugify`(`service.go:1077`)改造为冲突时追加 `-2`/`-3` 后缀(Discourse/Flarum 做法),并在 `topics` 表加 `UNIQUE(slug)` 约束(需迁移,并先去重现有数据)。`id_slug`/`id` 模式下 slug 仍允许重复,不强制唯一。

### 4. canonical/301 在 SSR 最早时机生效
当前详情页用 `watchEffect`+`navigateTo({redirectCode:301})`(L56-69),SSR 下时机偏晚且非真正 HTTP 301 响应。改为 `definePageMeta({ middleware: ... })` 或 `validate()` 在 SSR 入口直接 `navigateTo(target, { redirectCode: 301 })`,确保:
- 模式切换后,旧形态 URL → 301 → 新规范形态。
- slug 变更后,旧 slug → 301 → 新 slug。
- `id_slug`/`id` 模式间切换:ID 保持稳定,301 永不失效;`slug` 模式下 slug 唯一化保证可回溯。

> **301 的语义边界**:v1 的 301 是「同一条帖子在不同 URL 形态/slug 间的规范化」,基于稳定的 ID/唯一 slug 兜底。**不支持**「跨模式历史映射表」——那需要落库旧 slug 历史表(`topic_redirects`),属 v2 增量。

## 风险与权衡

| 风险 | 缓解 |
|---|---|
| catch-all 路由与 `/c/:slug`、`/tags/:slug` 冲突 | catch-all 限定在 `/t/**` 前缀下,与 `/c/`、`/tags/` 互不干扰 |
| `slug` 模式下 slug 冲突 | 迁移先去重 + `UNIQUE` 约束 + 创建时自动 `-2` 后缀 |
| 编辑页路由结构变化 | 显式迁移 `edit.vue`,保留 `forumTopicPath` 统一出口 |
| 旧外链(被搜索引擎/外站收录) | ID 稳定 → ID 类模式永不变;`slug` 模式唯一 slug → 可回溯;`id_slug↔id` 互相 301 |
| sitemap 产出形态错配 | Commit 2 同步改造 sitemap URL 生成 |
