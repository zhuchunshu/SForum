Go 1.25 新特性对 goroutine 调度器的改进实测

陈昊 版主
· 2 小时前 · 47 回复 · 1,236 浏览

Go 1.25 正式发布后，我对调度器做了一轮基准测试。重点关注 runtime 在高并发短任务场景下的表现，以及新引入的 goroutine 分组调度机制对延迟的影响。

测试环境

  • CPU: AMD Ryzen 9 7950X (16C/32T)
  • Go 版本: 1.24.3 vs 1.25.0
  • 负载: 每秒 50 万个轻量 goroutine，生命周期 2ms

核心结论

在 P 数量等于物理核数的场景下，尾延迟 P99 从 3.2ms 降到了 1.8ms，下降约 44%。关键改动在调度器的本地队列唤醒策略：

// 1.25 之前：全局 runnext 直接 hand-off
// 1.25 之后：引入 groupsched，按 NUMA 亲和性分组唤醒
func schedule() {
    if gp := groupsched.acquire(); gp != nil {
        execute(gp)
        return
    }
    // fallback 到全局队列
}
注意：这个改进只对 GOMAXPROCS > 8 的场景明显，单核或双核机器上几乎无变化。

数据对比

完整的基准数据和 flamegraph 我放在了 GitHub Gist，下面是关键指标摘要：

  • P50 调度延迟：0.8ms → 0.6ms（-25%）
  • P99 调度延迟：3.2ms → 1.8ms（-44%）
  • 每秒 goroutine 吞吐：480k → 520k（+8%）

欢迎大家一起讨论你们的测试结果。

补充一个生产环境的数据点：我们在 32 核物理机灰度了一周，P99 调度延迟从 4.1ms 降到 2.3ms，GC STW 没变化，整体吞吐提升约 8%。
